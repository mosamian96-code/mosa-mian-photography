2026-08-19 — Bug fix: TOTP enrollment/verification always failed with a misleading "code didn't match" error. Root cause: the JWT session callback in src/lib/auth/config.ts never copied the user id from `token.sub` into `session.user.id`, so every route checking `session.user.id` (MFA enroll/verify) silently 401'd regardless of the code entered -- confirmed via temporary server-side logging showing hasSession:true, a valid email, but userId:undefined. Fixed by adding `if (token.sub) session.user.id = token.sub` to the session callback; took effect immediately for the existing session cookie, no re-login needed, since token.sub was already set correctly at sign-in. Also stopped the client from showing "code didn't match" for a 401 (now says the session expired), so a future auth bug like this surfaces correctly instead of looking like a wrong code.

2026-08-20 — Bug fix, round 2 (the real fix): diagnosed by downloading a real uploaded CR3 and inspecting it directly with exiftool (scripts/diagnose-orientation.ts, since removed). Found: RAW container Orientation=8, but the extracted JpgFromRaw preview's own Orientation tag is `undefined` -- the rotation info lives only on the RAW file's own EXIF, not on the embedded preview exiftool pulls out of it. `.rotate()` with no args only reads whatever orientation tag is on the buffer it's given, so on the preview buffer specifically it was silently a no-op the whole time; plain JPEG/HEIC uploads were never affected (their own file's EXIF carries a real tag). Fixed by adding `normalizeOrientation(buffer, orientationCode)` to derivative.ts, which applies a numeric EXIF orientation code explicitly via the standard 8-value transform table, and calling it in worker/process-ingest.ts's extractRasterBuffer with the RAW container's `tags.Orientation` -- not relying on the preview buffer's own (absent) metadata. Verified with a test asserting an 800x600 buffer carrying no orientation tag becomes 600x800 when explicitly given orientation 8.
